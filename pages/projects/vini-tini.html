01 The problem — and why "just use an API" wasn't the answer

Commercial LLMs are brilliant and borrowed: your prompts leave the building, your assistant lives in someone else's pricing tier, and nothing runs when the internet doesn't. I wanted an assistant that lives on my desk, answers in milliseconds, knows nothing leaves the room — and keeps working during power-cut-induced network blackouts. That constraint set points exactly one direction: small models, local hardware.

The stakeholders here are unusual but real:

  • Me, as the user — an assistant that handles reminders, timers, Q&A, IoT toggles, and tool routing without phoning home.
  • Developers like me — who want a compact coding model specialized for TypeScript backend work, inspectable and Apache 2.0 licensed.
  • The edge itself — Raspberry Pis and old desktops deserve useful AI without 24GB VRAM.

02 My role

Sole researcher-engineer. Dataset collection and curation, tokenizer strategy, training-loop implementation in PyTorch, evaluation harnesses, and deployment packaging — the full pipeline from raw text to a model with a job. This is research discipline applied to product instincts: every experiment logged, every checkpoint versioned, every failure kept as evidence.

03 Why BitNet b1.58

BitNet b1.58 quantizes weights to three values — −1, 0, +1 — replacing most multiplications with additions. The payoff is brutal efficiency: dramatically smaller memory footprint and energy-per-token, which is precisely the currency of edge devices. For an assistant meant to live on a Raspberry Pi, ternary weights aren't a compromise — they're the enabling technology. Both models share this architectural spine; only their diets differ.

04 Training them

  • Vini (the assistant): trained on curated instruction data spanning conversational Q&A, command parsing, and tool-routing traces — because an assistant's real skill is deciding which tool, not just generating text. Repo structure carries models/, docs/, and shared configs so experiments reproduce.
  • Tini (the coder): fed a diet of TypeScript backend code — configs, data collection pipelines, inference and deployment directories all versioned. Trained notebooks and a HuggingFace dataset ship alongside the model.
  • Evaluation: both models run against task-level benchmarks (does the timer actually get set? does the code actually compile?) rather than vanity perplexity alone.

05 Shipping it

Tini is published on HuggingFace at jayptl-rq/tini under Apache 2.0 — model card, dataset references, and deployment configs included. Vini stays closer to home by design: it's the living brain of my self-hosted ecosystem, wired into Ollama-based local inference, n8n workflows with MCP connectors for tool calls, and Qdrant vector storage for retrieval over my own corpora. Research that never runs daily is just a notebook graveyard — Vini runs daily.

06 What it proves

  • ML engineering beyond API consumption: tokenizers, training loops, evals, quantization-aware architecture choices — owned end to end.
  • Open-source contribution with real hygiene: license, docs, reproducibility artifacts.
  • Systems thinking across the full AI stack — training, serving (FastAPI/Hono), orchestration (n8n + MCP), and retrieval (Qdrant/Chroma).
  • Judgment about trade-offs: knowing when 1.58-bit ternary weights beat a 70B parameter cloud bill.

07 What I learned

Data quality beats architecture cleverness more often than Twitter admits. Evaluation is the actual product — a model without a benchmark you trust is a vibe. And there's something clarifying about hardware limits: when your model has to fit on a board the size of a credit card, every design choice becomes honest.
